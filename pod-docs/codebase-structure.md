# Codebase structure

A client-side chess web app: Vite + React 18 + TypeScript + Redux Toolkit, deployed to GitHub Pages under `/chess-web/`. No backend, no database, no auth; all state is in the browser (Redux store).

## Layout

- **`index.html` → `src/index.tsx` → `src/App.tsx`**: the root `index.html` is the Vite entry and loads `/src/index.tsx` as a module. `index.tsx` wraps the app in the Redux `Provider` and the `DndProvider` from `react-dnd-multi-backend` with its `HTML5toTouch` preset (mouse uses the HTML5 backend, the first `touchstart` switches to the touch backend), plus a touch-only drag preview that draws the dragged piece at the square size (the `PieceDragPreview` component in the board's `components` folder); `App.tsx` renders the board. Single screen, no router.
- **`src/app/`**: the Redux store (`store.ts`, a `board` reducer and a `view` reducer) and typed hooks (`hooks.ts`).
- **`src/features/board/`**: the UI and Redux state for the game.
  - `Board.tsx` and `components/*` (`Square`, `Piece`, `Promotion`, `Notation`, `GameOver`, `FallenPieces`, `Player`, `BoardSidebar`, …): presentation; drag-and-drop via `react-dnd`, animation via `framer-motion`.
  - `src/features/board/BoardSlice.ts`: the Redux reducer. It keeps one engine `GameState` per ply (`engineHistory`), asks the engine for legal moves and applies moves through it, and keeps the UI-only parts itself: notation, last-move highlight, fallen pieces, the promotion picker step.
  - `src/features/board/engineAdapter.ts`: the bridge between the pure engine and the UI. It turns a `GameState` into the `HistorySquares` grid the UI reads, builds engine `Move`s from UI actions, maps the picker choice to a promotion kind, and reports the checked king and game-over state.
  - `orientation.ts`: pure board-to-screen math for the flip. Board coordinates stay White's view everywhere (`y = 0` is rank 8, `x = 0` is the a-file); `toDisplay`, `displayOrder`, `squareLabels` and `promotionPlacement` map them to where a square renders, which squares carry the rank and file labels, and where the promotion picker sits.
  - `viewSlice.ts`: the `view` reducer, `{ flipped, soundOn }`. `toggleFlip()` turns the board around; it isn't saved. `toggleSound()` turns move sounds on or off; the Sound button saves it, and the slice loads it at start. The board `reset` touches neither. `Board.tsx` renders squares in `displayOrder(flipped)` with each square keyed by its board index, swaps the player cards (keyed by color, so each clock stays with its player), and wraps the board in framer-motion `MotionConfig reducedMotion="user"`. The Flip button blocks the layout animation for the flip render, so pieces jump instead of sliding.
  - **Move sounds:** `src/features/board/sound.ts` holds the `SoundKind`s, the `SOUND_FILES` map, `pickSound` (game end > check > promotion > castle > capture > move) and `soundToPlay` (play a stored sound only when it's a new object and sound is on). `BoardSlice` stores `moveSound: { kind } | null`, a new object per completed ply (a promotion completes on the pick). `src/features/board/soundSetting.ts` loads and saves the setting in `localStorage` under `chess-web.sound` (`"on"`/`"off"`, default on, storage errors ignored). `src/features/board/soundPlayer.ts` is the Web Audio player: `install` fetches the files and waits for the first user gesture to make and resume the `AudioContext`; `play` starts a decoded buffer through one gain node and sets `data-last-sound="<kind> <n>"` on `<html>`. Its browser parts are injected, so the tests use fakes. `src/features/board/useMoveSound.ts`, mounted once in `Board.tsx`, installs the app's single player and plays each new `moveSound`.
  - `squareMarks.ts`: pure choice of the marks a square shows (highlight tint, dot or ring hint, check glow, drop edge); `Square` only renders what it returns. Mark colors come from the `--board-*` tokens in `src/index.css`.
  - `src/features/board/clock.ts`: pure clock math in whole milliseconds (drift-free countdown from `Date.now()` passed in, `MM:SS` / tenths format, low-time stages, the hand's quarter-turn angle, phase and tick interval, the 10s alert text). No React, no timers.
  - `src/features/board/components/Player.tsx` keeps each player's `ClockState` and one timer per turn (keyed on `tickInterval`, each tick timed to land when the digits change), and dispatches `stop()` on flag fall or game over. `PlayerClock.tsx` is the presentational pill: `role="timer"`, inline SVG clock face whose hand jumps 90° per second, digits, and a hidden `role="alert"` sibling at 10s.
  - `src/features/board/components/avatar.ts`: `avatarSrc(name)` maps a player's avatar file name to its imported image URL through a static map, falling back to `chess-player.png`. Add a line there when `src/game/players.ts` uses a new avatar.
- **`src/features/liem/`**: vs Liem, the ladder: sparring bots at 1400 to 2500 and Le Quang Liem himself at the last step, all playing his book, then Stockfish. The page opens here. `matchSlice.ts` (store key `match`: mode, which starts as `"liem"` with the setup card open and isn't saved; setup card, color pick, strength, his last choice, his status), `levelView.ts` (every text a level shows: the card's name, detail and phone detail, the setup card's value, step label and engine line, the out-of-book text; components add no words of their own), `liemActions.ts` (switch mode, New game, Start game), `liemTurn.ts` (whether it's his turn), `opponentController.ts` (loads him once, drops stale answers, retries), `bookNote.ts` (the note and badge view), and `liemOpponent.ts` (loads both books and the Stockfish worker). `useLiemOpponent.ts`, mounted once in `Board.tsx`, makes one controller per mount (disposed on unmount, so StrictMode's second mount gets a fresh one), preloads him once a vs-Liem game starts, asks him on each of his turns and cancels otherwise, and plays his answer with `playOpponentMove` then `opponentMoved`. It imports `liemOpponent.ts` with a dynamic `import()`, so Stockfish and the books stay out of the entry bundle (`tests/build.test.ts › engine and books load lazily`).
  - **Layout (`Board.tsx`):** the mode tabs sit above the board in both modes. **Two players** is the old layout: a card above and below the board, then Play, Reset, Flip and Sound. **vs Liem** keeps a card above and below the board, like Two players, so `.squares` never moves on a tab switch: his card (his name, title and avatar from `LIEM.entry`, with `LiemCardDetail`) on his color's side and the "You" card on yours, following the flip. At 1400 to 2500 his card is the sparring bot's: the ♞ glyph (`Player`'s `glyph`, `.liem-sparring-avatar`) in place of a photo, "Sparring · N" and "Plays Liem's openings", no GM tag or star. At the Liem step it's his photo, GM tag, gold star (`Player`'s `nameMark`) and "GM · 2732". In a game your color is `humanColor`; with the card open it is the color picked so far (Random shows White). `Board.css` holds every `.board > .player` at 56 px, so his two-line card is as tall as a plain one. Below 768 px the line drops "Plays " (sparring) or "GM · " (Liem) from sight and the badge drops its count; screen readers still get the whole line, and what still doesn't fit ends in an ellipsis. **vs Liem with the card open:** the setup card sits inside `.squares` over the squares, which are dimmed (`.squares__grid.liem-dimmed`, no pointer events); the buttons are Flip and Sound. **vs Liem in a game:** the sidebar shows the book note (`.liem-side`), then New game, Flip and Sound (no Play or Reset), Fallen Pieces and Notation. At 992 px and up `.app` is a row (board left, sidebar right); below that everything stacks in that order. On a 312 px board the setup card hangs below the board rather than being cut off.
- **`src/features/review/`**: the post-game review of a vs-Liem game (plan `post-game-review`). `reviewSlice.ts` (store key `review`: open, the game it belongs to, status, one eval per position, the cursor, the graph side, key-moment statuses, the phone sheet; `reset` and `newGame` clear it), `reviewActions.ts` (when **Review game** works: a finished vs-Liem game with a move of yours and no promotion to pick; Back to game; where the pass starts; trying a move at a key moment; arrow keys; the guarded `buildReview`), `reviewLimits.ts` (`REVIEW_LIMITS`, see `pod-docs/decisions.md`), `keyMomentView.ts` (the card's state), `tryBoard.ts` (click-to-try rules) and `graphGeometry.ts`. `useGameReview.ts`, mounted once in `Board.tsx`, runs the analysis pass on his engine through `useLiemOpponent`'s `analyse` while the review is open and analysing (stopped on close or a new game), loads his books once with a dynamic `import()`, builds the model and handles tried moves and the arrow keys. `components/` holds the prop-driven `ReviewGraph`, `ReviewBoard`, `KeyMomentCard`, `BottomSheet`, `MoveList`, `AccuracyPanel`, `LeftBookNote` and `StepButtons`; their look is `src/styles/review.css` with the `--grade-*` and `--review-*` tokens.
  - **Layout (`Board.tsx`):** in the review, `.review` (no box of its own) holds B's graph full width above the board and sidebar (`.app` becomes a two-column grid at 992 px and up), the `ReviewBoard` in `.squares` with the player cards around it and the step buttons under it, and the sidebar: the key-moment card, accuracy, move list, "Left his book" note, then Back to game, New game, Flip and Sound. Below 768 px it all stacks and the card is in the bottom sheet, which sits low (no scrim) while you try a move.
- **`src/game/engine/`**: the pure rules engine, the only one the app uses. Immutable `GameState` (`game-state.ts`), `legalMoves`/`applyMove` (`engine.ts`), per-piece move generators and shared geometry (`moves/`), attack map and check (`moves/attack.ts`), checkmate/stalemate (`game-status.ts`), promotion ids (`moves/promotion.ts`). Fully unit-tested, including perft counts and a replayed recorded game.
  - `PROMOTED_IDS` in `src/game/engine/moves/promotion.ts` is the single table of promoted-piece ids (`*Promoted1..4`, at most 4 per type). `src/constants.ts` re-exports it as `PromotionBoard` for the picker.
- **`src/game/opponent/`**: the computer opponent that plays like a real player (sprint `liem-book` of plan `play-like-liem`). Pure TypeScript, no React.
  - `position.ts`: the codec between engine `GameState`/`Move` and text. `squareName` (`[7,4]` is `e1`), `moveToUci`, `uciToMove` (returns the matching move from `legalMoves`, or `null` for anything not legal, including a missing or extra promotion suffix), `positionKey` (FEN fields 1 to 4; the en-passant square is written only when the side to move has a legal en-passant capture, so transpositions share a key) and `toFen` (the key plus counters, default `0 1`).
  - `types.ts`: the book format (`Book`, `BookMove` tuple `[uci, win, draw, loss, otb, lichess, chesscom]`, `BookName`, `GameSource`), the `PlayerEntry` type, and the `moveGames`/`positionGames` count helpers.
  - `engine/`: the Stockfish boundary, `MoveEngine` and `EngineError` (`move-engine.ts`), the UCI protocol (`uci-engine.ts`) and the Web Worker glue (`stockfish-worker.ts`). `analyse(fen, limits)` runs one MultiPV search (`go depth D movetime T`, `MultiPV` lines) and returns the scored top lines (`EngineLine`, `lines.ts`) plus `bestmove`. The app never sends `UCI_LimitStrength` or `UCI_Elo`.
  - `book.ts`: picks the book for the game clock (`bookForClock`), looks a position up with the thin-line fallback (`lookupBook`) and makes the weighted pick.
  - `opponent.ts`: `createOpponent`, which chooses a move from the book, else from the engine's lines, and returns only moves in `legalMoves`. `strength.ts` holds the strength steps; `step-profiles.ts` holds `STEP_PROFILES`, each step's search limits and pick rules, including each sparring level's `mistakeChance`, `blunderChance`, `blunderMaxCp` and `hangWeight` (all required; Liem's are 0). The values come from `npm run calibrate` and its measure mode, see `## Calibrating the strength steps`; going up the steps, depth never falls and the loss limits, chances, `blunderMaxCp` and `hangWeight` never rise. A search stops at whichever comes first, its depth or its `movetimeMs`. Full's real limit is time: at 1000 ms it stops at depth 13 to 16 and never reaches its depth 18, yet it still plays Stockfish's best move. The 1 s limit stays so phones answer quickly.
  - `human-move.ts`: `chooseHumanMove`, the pick a human of the step's strength would make among the engine's lines: play a seen mate within `forceMateIn`, avoid walking into a mate, drop lines other than the best that hang material (`material.ts`, `hangsMaterial`), never skip a capture that nets 3 or more (`materialNet`) for a line that wins less unless the engine rates that line better, then pick within `maxLoss` win % points by `exp(-loss / temperature)`, with a rare slip (`slipChance`) up to `slipMaxLoss`, and a tighter `aheadMaxLoss` when well ahead. A line 300 cp or more below the best (`MAX_DROP_CP`) is outside every limit, because win % flattens when one side is far ahead and a lost piece costs only a few points. Before those picks, a sparring level that is not well ahead (top line under `AHEAD_WIN`, 85 %) draws once: under `blunderChance` it picks from the **blunder band** (loss ≥ 30 win %, and under `blunderMaxCp` cp when both scores are cp), under `blunderChance + mistakeChance` from the **mistake band** (20 to under 30, and under `MAX_DROP_CP`). Band lines are weighted `exp(-(loss - least) / 10)`, times `hangWeight` for a line that hangs material; an empty band falls back to the normal pick. Liem's chances are 0, so he never draws.
  - `players/`: one folder per player (`player.json` and the two committed book JSON files), plus `index.ts` exporting `PLAYERS` and `LIEM`. Nothing outside this folder hard-codes a player's data.
  - **Relative imports only** under `src/game/opponent/` (no `game/` aliases), so the Node import script under `scripts/` (run with `tsx`) and its tests can load it.
  - **No PGN parser in the app:** `chess.js` (or any PGN parser) is imported only under `scripts/`, never under `src/`. Raw PGN stays in the git-ignored `/games/` folder.
- **`src/game/review/`**: the review model, pure TypeScript with relative imports. `moves.ts` (each ply's UCI move and its `13.Nd5` / `13...Nc6` label), `grade.ts` (win %, drop, accuracy, the 10/20/30 grades, the mate rules and the found rule; `gradeMove` takes optional levels, such as `LICHESS_LEVELS` 5/10/15, and is the only place a move is graded), `build-review.ts` (`buildReview`: graded moves, game accuracy, his book plies, where the game left his book and the 3 key moments) and `analysis-runner.ts` (one search at a time over the game, with tried-move checks jumping the queue).
- **`scripts/book/`**: the Node import script that builds the books (run with `tsx`, never bundled). `timecontrol.ts` (clock estimate and slow/online class), `games.ts` (PGN to his filtered, deduped, colored games, parsed with `chess.js` and replayed through `uciToMove`), `build-book.ts` (games to the two `Book`s, the `minGames` floor and the 3 MB budget, byte-stable JSON), `sources.ts` (Lichess account, Lichess export, Chess.com monthly archives, retries on 429, all through an injected `fetch`), and `import-book.ts` (`runImport` plus the thin CLI). Tests in `scripts/book/__tests__/` use fixture PGN and HTML only.
- **`scripts/calibrate/`**: the dev-only calibration script (run with `tsx`, never bundled, never in tests or CI). `match.ts` (openings, one game, a pairing's tally and Elo gap, all with injected players), `anchor.ts` (Stockfish at a set `UCI_Elo` through its own small UCI player, and the Node glue that runs one Stockfish per child process), and `calibrate.ts` (flags, the game pool, the per-step tables). Tests in `scripts/calibrate/__tests__/` use fake players and a fake UCI pipe only.
- **`scripts/ladder/`**: the dev-only human baselines for the sparring ladder (run with `tsx`, never bundled, never in tests or CI). `rates.ts` (`measureGames`: per-40-move inaccuracies, mistakes and blunders at the review's 10/20/30 and Lichess's 5/10/15, hung pieces, missed captures, average win % loss and accuracy, all graded through `gradeMove`; plus `targetFor` and `withinTarget`, the 75 % target and its 25 % tolerance), `lichess.ts` (the polite Lichess client, the arena and game endpoints, Lichess evals to side-to-move evals, the rating band) and `baseline.ts` (flags, collecting players and games, the file and its summary). `human-baselines.json` is the committed output. Tests in `scripts/ladder/__tests__/` use inline fixtures and a fake `fetch` only. See `## Human baselines`.
- **`src/game/pieces/*`**: presentation only. Each piece class holds its image, weight and notation letter; no move rules and no game state. `src/game/piece-factory.ts` maps a `PieceType` to its piece object, and `src/game/piece-notation.ts` writes move notation.
- **`src/game/board-types.ts`**: the UI board types, `Square` (`{ pieceType, isEnemyAttacked }`) and `HistorySquares`.
- **`src/game/piece-type.ts`**: the `PieceType` enum, including the promoted ids. `src/game/players.ts` holds the two players' names and avatars.
- **`src/constants.ts`**: the start position, `PromotionBoard`, square sizes and the default clock time. It is imported by relative path; `constants` is not a bare-import prefix.
- **`src/assets/`**: piece SVGs, avatar PNGs and the self-hosted Quicksand fonts (`fonts/`).

## Stack & conventions

- **Toolchain:** Vite 8 (`vite.config.ts`) with `@vitejs/plugin-react` 6, Vitest 5, TypeScript 5.x (below 6). Node 22.12 or newer (Vitest 5 needs it); local is Node 24. React 18, Redux Toolkit 1.x, react-dnd 16 (with `react-dnd-multi-backend` 9 for touch) and framer-motion 7.
- **Scripts:** `dev` = `vite`, `build` = `tsc --noEmit && vite build` (Vite only transpiles; `tsc` type-checks `src/` only, not `vite.config.ts` or `tests/`), `preview` = `vite preview`, `test` = `vitest run`. Build output goes to `dist/`.
- **Base path:** `base` is `/chess-web/` in dev, build and preview. Files in `public/` are referenced as `/x`, never `%PUBLIC_URL%`.
- **Bare imports:** `app/`, `assets/`, `features/`, `game/` and `hooks/` resolve to `src/<prefix>/`. The single source is tsconfig `paths` (no `baseUrl`); Vite reads it through `resolve.tsconfigPaths`. Anything else, such as `constants`, is imported by relative path.
- **Sounds:** move sounds live in `public/sounds/` (one `.wav` per kind, each under 100 KB), with their source and CC0 licence in `public/sounds/CREDITS.md`. Vite copies them to `dist/sounds/`; the player loads them from `${import.meta.env.BASE_URL}sounds/`.
- **Clock colors:** the player clocks use only the `--clock-*` tokens in `src/index.css` `:root` (waiting, running and low pairs; the low pair is for the large digits and icon only). Quicksand 500 and 700 (latin woff2) are self-hosted in `src/assets/fonts/` with their SIL OFL licence (`OFL.txt`), loaded by `@font-face` rules (`font-display: swap`) in `src/index.css`; Vite emits them to `/chess-web/assets/`. No CSS under `src/` loads anything over http(s).
- **vs-Liem look:** `src/styles/liem.css` (imported from `src/index.tsx`) holds the `.liem-*` classes for the mode tabs, setup card, color tiles, strength steps, Book badge, book note and the dimmed board. Its colors come only from the `--liem-*` and `--book-bar` tokens in `src/index.css` `:root` (plus `--board-focus` for the 3 px focus ring). Flag red is for edges and underlines, never text.
- **SVGs:** never inlined (`build.assetsInlineLimit` returns `false` for `.svg`), because `Piece.tsx` and `Promotion.tsx` put image URLs in an unquoted CSS `url(...)` that a `data:` URL breaks.
- **Tests:** Vitest with `environment: 'node'` (no jsdom). Components may be tested in node by rendering to a string with `react-dom/server`'s `renderToStaticMarkup` (wrap in the Redux `Provider` with the real store if they read it); effects and timers don't run there, so keep timing logic in pure functions. Tests live in `__tests__/` folders under `src/` (they run through the app's own imports and aliases) and in the root `tests/` folder (tests that read files or run processes with Node APIs; `tsconfig` gives `src/` only `vite/client` types).
- **SVG mock:** under Vitest only, every `*.svg` import resolves to `src/__mocks__/svgMock.ts` (default export `"svg-mock"`). The production build bundles the real SVGs.
- **ESM package:** `package.json` has `"type": "module"`, so any Node script at the repo root must be ESM or be named `.cjs`.
- **Deploy:** GitHub Actions builds and publishes `dist/` to GitHub Pages on push to `main`; there is no local deploy script. See `## CI`.

## Smoke recipe

The app is a static single-page client; there is no server, database or login to stand up.

- **Install:** `npm install` (plain, no flags). Each worktree installs its own `node_modules`. A `node_modules` left from an older install (CRA era, or installed with extra flags) is stale: delete it and install again before running tests. On Windows the first install can leave a corrupt tree (for example an invalid `@rollup/rollup-win32-x64-msvc`); delete `node_modules` and install once more.
- **Dev:** `npm run dev` → `http://127.0.0.1:${PORT:-5173}/chess-web/`.
- **Production check:** `npm run build && npm run preview` → `http://127.0.0.1:${PORT:-4173}/chess-web/`. Use this to catch base-path problems (missing images, blank page).
- **Ports:** both servers bind `127.0.0.1`. Set `PORT` to a whole number from 1 to 65535 to pick the port (PowerShell: `$env:PORT=3030; npm run dev`); anything else falls back to the defaults above.
- **DB setup / login:** none.
- **What you see:** the "vs Liem" / "Two players" tabs (vs Liem selected) and the "Challenge Le Quang Liem" setup card over the dimmed 8×8 board in the start position, with the sparring bot's card above ("Sparring · 2100", the ♞) and "You" below, notation and fallen pieces in the sidebar, and Flip and Sound buttons (Sound is green when on). Click **Two players** (`role="tab"`) for the two-player board: two player cards with avatars and Play, Reset, Flip and Sound. Pieces move by drag-and-drop or by clicking (or tapping) a piece and then its target square; a `GameOver` overlay appears on checkmate or stalemate.
- **Runtime to smoke:** load the page and click **Two players**: no console errors and all piece images and both avatars showing; make a legal move and see it reflected; then play **castling, en passant, pawn promotion (promotion picker) and a checkmate (GameOver overlay)**; reset and play a second game to confirm state clears. Per-slice `Runtime to smoke` lines in engineer summaries name what a given slice adds.
- **Play by clicking:** each square has `data-square="<file><rank>"`. Click the piece's square, then the target square, for example `document.querySelector('[data-square="e2"]').click()` then `[data-square="e4"]` in one `eval`. This works after **Play** too, with no drag workaround.
- **Flip:** click **Flip board** (`aria-label`). The board turns (h1 top-left), the labels stay on the left and bottom edges, the white card moves to the top, and `aria-pressed` turns `true`. Pieces jump, they don't slide. Then play moves by click and by drag on the flipped board and check they land on the named squares; `data-square` names board squares, so the same selectors work flipped. Play a promotion (the picker opens beside the pawn) and a checkmate while flipped, and press Play then flip mid-game to see each clock stay with its player.
- **Sound:** browsers only unlock audio after a real user gesture, and a click from page JS doesn't count, so first give one real click with the tool's `click` (for example on the Notation heading). Then play a move, a capture, castling, a check, a promotion and a mate, and after each read `document.documentElement.dataset.lastSound` in an `eval`: it's `"<kind> <n>"`, with kind `move`, `capture`, `castle`, `check`, `promote` or `game-end` and `n` counting up. Toggle **Sound** (`aria-label="Sound"`) off, play a move and see `data-last-sound` unchanged, then reload and see the button still has `aria-pressed="false"` (`localStorage['chess-web.sound']` is `"off"`).
- **Phone (375 px):** `emulate --viewport "375x812x2,mobile,touch"` (`resize` stops at 500 px). The button row wraps. Play a full game by tapping squares (click from page JS, see `pod-docs/known-issues/browser-smoke-touch.md`): castling, en passant, promotion and checkmate, with no console errors. To drag pieces by touch, follow the touch drag run in `pod-docs/known-issues/browser-smoke-touch.md`.
- **vs Liem:** the page opens on vs Liem, so the steps above need one click on **Two players** first. Before Start game the Network tab has no `.wasm`, `stockfish-*` or `book-*.json` request. On load the setup card (`role="dialog"`, `aria-label="Challenge Le Quang Liem"`) is over the dimmed board. The card's value reads "about 2100" (the last step reads "★ Liem" in gold, `aria-label="Liem (2732)"`), and under the steps, above Start game, a soft-text line reads "A sparring bot plays his openings, then Stockfish at about 2100." ("Le Quang Liem: his openings, then full-strength Stockfish 18." at the Liem step) (`.setup-card__engine`); at 375 px the whole card fits inside the 312 px board. Pick a color tile and a strength step (`role="radio"`), then click `[role=dialog] .button--play` (Start game; the board's Play button has the same class). The books, `liemOpponent-*.js`, `stockfish-worker-*.js`, `stockfish-18-lite-single-*.js` and its `.wasm` load once from `/chess-web/assets/`; later games reuse them. As Black the board flips and he moves at once. `.squares` top is the same (100 px at 1400 and 375 px) in Two players, with the card open and in a game; his card, above or below the board, shows "Thinking…" and then the badge. Read the note's `data-book-state` (`waiting`, `in-book`, `out`, `failed`); in book each row has `data-uci` and `data-played`, and the badge's `data-book-games` equals the note's total. Keep playing by clicking squares (his reply lands within a few seconds out of book) until the note says "Out of his book" with "Stockfish at about 2100 plays from here. It isn't trained on his games." ("Full-strength Stockfish 18 plays from here. …" at the Liem step) (as White, 1.h4 usually leaves his book at once). Out of book his card shows the grey pill `[data-engine="stockfish"]` ("Stockfish") where the "★ Book · N" badge was, and "Thinking…" replaces it while he thinks; his clock doesn't move. At 1400 to 2500 his card reads "Sparring · N" with the ♞ and "Plays Liem's openings" ("Liem's openings" below 768 px); at the Liem step his photo, GM tag, gold star and "GM · 2732" ("2732" below 768 px). The badge reads "★ Book · N" (just "★ Book" below 768 px); the full text stays for screen readers. New game (in the button row) ends the game and reopens the card; pressing it while his card says "Thinking…" never plays the stale move. As White, 1.f3 then 2.g4 lets him mate with Qh4# (GameOver overlay). The tiles have no `aria-label`; their text starts with the glyph (`♔White`).
- **Game review:** finish a vs-Liem game (as White, 1.f3 e5 2.g4 lets him mate at once; or let your clock run out after a move). **Review game** shows in the button row only then, never in Two players or mid-game. ## Building the books

`npm run book:import` rebuilds `src/game/opponent/players/le-quang-liem/book-slow.json` and `book-online.json`. It runs by hand, never in CI or tests, and **it calls the live Lichess and Chess.com APIs**. Commit the two JSON files it writes.

- **Flags:** `npm run book:import -- --lichess-user <name>` sets the Lichess account. Without it the script uses `sources.lichessUser` in `player.json`, else the account linked from the Lichess FIDE page (`sources.lichessFideUrl`). If none resolves, it warns and builds without Lichess.
- **`games/` (git-ignored):** put his over-the-board PGN files in `games/otb/*.pgn` (for example from TWIC). Downloads are saved in `games/cache/`; finished Chess.com months are read from there on the next run, and the archive list, the current month and the Lichess export are always fetched again.
- **Output:** the script prints the Lichess account used, games read and kept per source, the skipped counts by reason, the games cut short at a rejected move, and per book the games, positions, `minGames` and size. If any source fails (an HTTP error, or still 429 after 3 retries one minute apart), it exits non-zero and writes no book.
- Every request sends `User-Agent: chess-web-book-import/1.0 (+https://github.com/iamphduc/chess-web)`. The rules for which games go into which book are in `pod-docs/decisions.md` (2026-10-09 entries).

## Calibrating the strength steps

`npm run calibrate` plays each strength step against Stockfish anchors and prints a table per step. It runs by hand, never in CI or tests, and it calls nothing on the network. Run it from a clean checkout, so the table it measures is the committed one.

- **What plays:** each step moves like `createOpponent` with empty books, the lite single-thread Stockfish build (the one the browser uses), `STEP_PROFILES[step]` and a seeded random. Its rivals are **anchors**, Stockfish with `UCI_LimitStrength` at a set `UCI_Elo` (1000 ms a move), and the next step up. Each engine runs in its own Node child process, because the npm loader can't hold two in one process.
- **Games:** from a fixed list of 8 short, balanced openings, each played once with each color. A game ends on checkmate or stalemate (our rules engine), or as a draw at 200 plies (no repetition or fifty-move rule). An error ends that game; it is listed, not scored.
- **Flags:** `--steps 1400,1700,...,full` (default all), `--anchors -200,0,200` (offsets from each step's Elo, Full's is his rating; clamped to Stockfish's 1320 to 3190; `none` keeps only the next-step pairing), `--anchor-elos 2400,3190` (the same anchors for every step, in place of the offsets), `--games N` (even, default 4), `--seed N` (default 1), `--jobs N` (games at once, default up to 6).
- **Output:** a progress line per game, then per step and rival: W/D/L, errors, score %, the Elo gap estimate `-400·log10(1/s − 1)` (with `s` clamped to `[0.5/n, 1 − 0.5/n]`), the Elo that implies against an anchor, the average and largest loss per move (win % points against the move's own search, from `MoveChoice.lines`), the slip rate (moves losing more than `maxLoss`), and average and max ms per move. Max ms includes the first move's engine start-up.
- **Time:** `--games 4` over all steps is 108 games, about 20 minutes at 6 jobs. Run it in the background with output to a log file.
- **Measure mode:** `npm run calibrate -- --measure [--steps 1400,...,2500,full] [--games N] [--seed N] [--jobs N]`. Each step plays itself from his book (the 10-minute book), one side resigns after 3 engine moves in a row at -1000 cp or worse, and a game is drawn at 200 plies. Every position is graded at the review's limits (depth 18 or 500 ms), and only engine plies count. Defaults: the six sparring steps, 20 games, seed 1. It prints, per step, the profile, games, graded moves and ms per engine move, then each rate per 40 moves (review and Lichess inaccuracies, mistakes and blunders, hung pieces, missed captures, average loss) as bot, human (from `scripts/ladder/human-baselines.json`), target (75 % of human) and `ok` (`yes` within 25 % of the target, for `review.mistake` and `review.blunder` only), then the three biggest drops with their FEN. Time at `--jobs 10` on 12 cores: 40 games of all six sparring steps about 30 minutes, with `full` added about 43 minutes. Run it in the background with a log, never in CI or tests. 40 games is still noisy (a rate moves about ±10 % between runs of the same table).
- Record each run that changes `STEP_PROFILES` (flags, results, the values chosen) in `pod-docs/decisions.md`. Four games per pairing is noisy: one game is ±12.5 %; read the trend across anchors, not one cell.

## Human baselines

`npm run baseline` measures how often real Lichess players near each sparring level (1400, 1700, 1900, 2100, 2300, 2500) make mistakes, and writes `scripts/ladder/human-baselines.json`. It runs by hand, never in CI or tests, and **it calls the public Lichess API** with no token or cookie. Commit the file it writes; `npm run calibrate -- --measure` compares the bots with it.

- **What it reads:** the players of recent finished standard blitz and rapid arenas (`/api/tournament`, then each arena's results), then, per level, the rated, analysed blitz and rapid games of the players within ±150 of it (closest first, 30 games a request, at most `--per-user` games a player). When the arenas run short (they rarely hold players rated 2300 and up), the opponents met in those games who are near the level are read next.
- **Which games count:** both players within ±100 of the level, edges included. Fewer than 30 widens it to ±150; fewer than 30 even then marks the level `lowSample`. Rapid games come first, then blitz up to `--games`. A game with an eval missing before its last ply is dropped and counted in `droppedGames`; a missing last eval in a live position leaves that ply out. A level with no games is left out of the file.
- **Grading:** each kept game is replayed on our rules engine and graded from ply `--skip-plies` with the review's `gradeMove`, both sides. Lichess's eval after each ply (White's view) becomes the side-to-move eval before the next ply; before ply 0 it uses +15 cp. `rates.accuracy` is the mean of Lichess's own per-player accuracy.
- **Flags:** `--games N` (kept per level, default 150), `--skip-plies N` (default 10), `--levels 1400,2500` (default all six), `--max-users N` (players read per level, default 60), `--per-user N` (default 8), `--max-arenas N` (default 25).
- **Politeness:** one request at a time, at least 1.5 s after the last one ended; a 429 waits (its `Retry-After`, else 60 s) and retries up to 3 times, through `fetchText` in `scripts/book/sources.ts`. Requests send only `Accept` and `User-Agent: chess-web-baseline/1.0`. A request that hangs 3 minutes fails, and that player is skipped.
- **Cache:** raw downloads go to the git-ignored `games/baseline-cache/` and are read back on the next run, the arena list included. Delete the folder for fresh data.
- **Output:** a progress line per player read, then one summary line per level (games, band, speeds, dropped, graded moves, the per-40 rates at both level sets, hung pieces, missed captures, average loss and accuracy). The file holds no usernames, game ids, game dates or moves.
- **Time:** the first run (2026-10-18, defaults) read 188 players in about 15 minutes, most of it waiting on Lichess to stream analysed games; a rerun from the cache takes seconds. Run it in the background with output to a log file.

## CI

One GitHub Actions workflow: `.github/workflows/pod-ci.yml`.

- **Triggers:** every `pull_request` (any target branch, including wave PRs into a plan branch), and `push` to `main` only. Pushes to other branches don't run it. To deploy again, re-run the `main` push run from the Actions tab.
- **`verify`:** Node 24 (`actions/setup-node`, npm cache), `npm ci`, then the smoke recipe's **Verification:** command (`npm run build && npm test`; `build` runs `tsc --noEmit`, so this is typecheck, build and tests). On a push to `main` it then uploads `dist/` as the Pages artifact; on a PR it uploads nothing.
- **`secrets`:** gitleaks (`gitleaks/gitleaks-action@v2`) scans the full git history (`fetch-depth: 0`).
- **`deploy`:** runs only on push to `main`, after both `verify` and `secrets` pass. It publishes `dist/` to `https://iamphduc.github.io/chess-web/` with `actions/deploy-pages`, in the `github-pages` environment. Only this job can write (`pages: write`, `id-token: write`); the rest are `contents: read`. Deploys queue (concurrency group `pages`) and never cancel each other. On a PR it shows as skipped.
- Actions are pinned to major tags (`@vN`). The only secret used is `GITHUB_TOKEN`.

**Human setup** (agents don't change repo settings):

- Before the first deploy from `main`: repo Settings → Pages → Source → "GitHub Actions". Until then Pages keeps serving the old `gh-pages` branch, and the `deploy` job fails. Rollback: switch Source back to the `gh-pages` branch.
- Decide whether `verify` and `secrets` become required status checks on `main`.
